Keep Unicode source content inside the right Git line

Preserving physical diff boundaries in PR-Agent’s reverse patching and supplied-diff parsing.

Upstream: The-PR-Agent/pr-agent · Pull request #4668 · Author: rudycelekli

The problem

Python’s splitlines() recognizes more separators than Git’s LF-based physical line model. A source line containing a Unicode line separator, NEL or form feed could be split into several logical lines, causing reverse patching to reject matching content or shift later hunk positions. A sibling supplied-diff parser could also lose continued source content.

Before

One Git source line containing U+2028 could become two Python splitlines() entries. A later hunk’s physical line number then referred to the wrong position.

After

Reverse patching uses the existing LF-aware splitter. Supplied-diff parsing uses LF-only StringIO iteration, and patch values remove only one line-ending CR rather than stripping all trailing carriage returns.

The contribution

The merged change adjusted both parsing paths and added regressions with non-LF separators inside source/context lines, a separator before a later hunk, and repeated trailing carriage returns. The existing EOF-newline policy and hunk-header contract were deliberately preserved.

Engineering lesson

Agentic code review depends on exact source reconstruction. Choosing a text splitter is a format decision: use the line model defined by the patch format, not a broader language convenience.
